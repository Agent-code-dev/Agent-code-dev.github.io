Skills

A skill is a folder. That's the whole system.

Skills vs add-ons: skills are drop-in skill.py folders that add tools and chat commands. Add-ons are trusted Python extensions that can also add UI, replace services, and hook lifecycle events. Need more than tools? See the Add-ons page.

Install, manage, publish

# Copy the three bundled skills into ./skills/

Disabling a skill

Toggle it off in agent-code manage → Skills tab. Disabled skills are not imported on the next launch; their folder stays put so you can re-enable.

Add-ons

Trusted Python extensions stored in <user-data>/addons/<id>/. Each add-on ships addon.json and addon.py; helper modules may live beside them.

Add-ons run with your OS permissions. They are not sandboxed. Install only code you trust. A future signed repository with hashes, compatibility metadata, permission declarations, and review is planned.

addon.py — skeleton

class AlternateSkillStore:
    base_url = "https://my-store.example/api"

    def list_skills(self):
        ...


def build_sidebar_button(parent, app):
    import customtkinter as ctk
    return ctk.CTkButton(parent, text="My workspace",
                         command=lambda: app.log_line("Workspace opened", "dim"))


def register(api):
    # Build arbitrary CustomTkinter widgets in supported application regions.
    api.register_ui("my-workspace", build_sidebar_button,
                    location="sidebar", label="My workspace")

    # Replace a named service when the relevant core integration opts in.
    api.register_service("skill_store", AlternateSkillStore(),
                         replaces=True, priority=50)

    # Add custom agent tools, slash commands, actions and lifecycle hooks too.
    api.on("tools_loaded", lambda **ctx: None)

UI extension points

register_ui(name, builder, location=..., label=..., description=...) supports sidebar, addons, settings, toolbar, and workspace. The builder receives (parent, app) and should return a Tk / CustomTkinter widget. The host places the returned widget. Keep builders fast — do not block the UI thread.

Service extensions

register_service(name, implementation, replaces=False, priority=0, description="") registers a named service implementation. AddonManager.resolve_service(name, default, app=...) returns the highest-priority registered implementation, or the supplied default. Factories can set addon_service_factory = True and accept app.

Service names are explicit extension points, not arbitrary monkey-patching of core globals. Core integrations must call resolve_service for a service before an add-on can replace it. Existing services remain the default when no add-on replacement is registered.

Lifecycle hooks

api.on("tools_loaded", callback) — subscribe to events. Callbacks receive keyword context.

Managing add-ons

Open the GUI with agent-code manage, then use the Add-ons tab. Disabling prevents the code from being imported on the next load — it does not reverse changes an already-loaded add-on made outside the API.

Trust and safety. Add-ons execute as your user account. Only install add-ons you trust. Do not run untrusted bundles from unknown sources.

Wrong key, or stray quotes in agent_config.json.

LLM ERROR: 404

Model name doesn't match the provider.

BLOCKED: command not allowed

Sandbox rejected the command.

externally-managed-environment
pipx install agent-code
addon failed to load

Check that addon.py defines a top-level register(api) function, and that addon.json is valid JSON with at least name, version, description, author.

addon UI widget does not appear

Confirm the location= you passed to register_ui is one of sidebar, addons, settings, toolbar, workspace. Builders must return a widget and should not block.

add-on service replacement has no effect

The core integration must call AddonManager.resolve_service(name, default) for that service — add-ons cannot monkey-patch globals. Check that the service name matches.

1. Overview

A skill is a self-contained folder that adds tools and/or chat commands to the agent.

Why skills? You never edit the agent source. Drop a folder in skills/, restart.

2. Skill anatomy

your-project/
└── skills/
    └── my_skill/
        ├── skill.py       ← code: metadata + tools + commands
        └── skill.md       ← docs: frontmatter + human notes

3. The contract

Hello World

SKILL = {
    "name": "greet",

}

def hello(name: str = "world") -> str:
    return f"Hello, {name}!"

        },
    },
}]

TOOL_CALLABLES = {"hello": hello}

6. Add-on development

Add-ons extend the agent beyond tools and chat commands — they can add UI widgets, replace named services, and subscribe to lifecycle events. Use them when a skill isn't enough. For the top-level overview and comparison table, see the Add-ons page.

Trust model: add-ons run with your OS permissions and are not sandboxed. Only ship code you'd run yourself.

Entry point — addon.py

Every add-on lives in <user-data>/addons/<id>/ and provides addon.py and addon.json. addon.py must define a top-level register(api) function; the host calls it exactly once on load.

{
  "name": "my-extension",
  "version": "1.0.0",
  "description": "Adds a custom workspace and alternate Skill Store client",
  "author": "Developer"
}
def register(api):
    api.register_ui("my-workspace", build_sidebar_button,
                    location="sidebar", label="My workspace")
    api.register_service("skill_store", AlternateSkillStore(),
                         replaces=True, priority=50)
    api.on("tools_loaded", lambda **ctx: None)

UI extension points

register_ui(name, builder, location=..., label=..., description=...) supports sidebar, addons, settings, toolbar, and workspace. The builder receives (parent, app) and must return a Tk / CustomTkinter widget. The host places the returned widget. Keep builders fast — do not block the UI thread.

Service extensions

Lifecycle hooks

Trust model
